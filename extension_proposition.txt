This file contains the proposition for the extension of the Wordpress project. 
Its objective is to give context to the LLM's inside the IDE's.

================================================================================
PROJECT EXTENSION SPECIFICATION: GEOGRAPHICALLY DISTRIBUTED MULTI-AZ CLOUD DEPLOYMENT
Course: Symbolic Explainable Artificial Intelligence (S-XAI) - 2026/27
Base Problem: CSPLib prob090 (WordPress Cloud Deployment)
================================================================================

1. OVERVIEW & MOTIVATION
--------------------------------------------------------------------------------
The base problem (CSPLib prob090) models the optimal deployment of a high-load, 
fault-tolerant WordPress application onto Cloud Virtual Machines (VMs) while minimizing 
leasing costs. It couples a Multidimensional Bin Packing Problem (BPP) with service 
topology constraints (require-provide, exclusive deployment, and anti-affinity/conflicts).

However, the base model assumes all VMs exist in a monolithic, flat infrastructure 
without considering real-world Cloud constraints such as geographic distribution, 
Availability Zones (AZs), cross-zone network latency SLAs, and data transfer costs.

To meet the non-trivial extension requirement, this project extends the base model 
into a **Geo-Distributed Multi-Region / Multi-AZ Architecture with Network Latency 
SLAs and Egress Traffic Costs**.


2. CORE OBJECTIVES OF THE EXTENSION
--------------------------------------------------------------------------------
1. Fault-Tolerance via Availability Zone (AZ) Anti-Affinity:
   - Ensure that redundant instances of critical components (e.g., MySQL cluster nodes, 
     Varnish cache replicas) are deployed across distinct Availability Zones to survive 
     single-zone outages.
2. Latency SLAs for Inter-Component Communication:
   - Model communication paths between dependent components (specifically, WordPress 
     instances communicating with MySQL database nodes) and enforce strict latency 
     thresholds based on the physical distance/zone of their host VMs.
3. Network-Aware Cost Optimization (Data Transfer / Egress Costs):
   - Expand the objective function beyond mere VM leasing prices to incorporate 
     inter-zone and inter-region data transfer costs, penalizing inefficient 
     topologies where high-volume traffic crosses expensive network boundaries.


3. WHY THIS EXTENSION IS NON-TRIVIAL (COMPLEXITY ANALYSIS)
--------------------------------------------------------------------------------
- From Bin Packing to Quadratic Assignment (QAP) / Network-Aware Placement:
  In the original model, placing component A on VM $k$ is independent of where component B 
  is placed, as long as capacity and conflict constraints hold. With this extension, 
  the cost and validity of a placement depend heavily on *where communicating pairs are 
  located relative to each other*.
- Increased Constraint Non-Linearity:
  Introduction of zone-mapping arrays, conditional distance checks, and aggregated 
  traffic matrices significantly increases the constraint propagation complexity and 
  search space for the MiniZinc solver (e.g., Gecode).
- Balance Between Feasibility and Optimality:
  The solver must simultaneously optimize hardware capacity, strict structural constraints, 
  fault-tolerance dispersion, and network routing costs.


4. PROPOSED MODELING SPECIFICATIONS FOR MINI-ZINC & PYTHON ORCHESTRATOR
--------------------------------------------------------------------------------

A. New Input Parameters:
   - `int: NoZones;` -> Number of available Availability Zones / Regions.
   - `array[1..VM] of 1..NoZones: VMZone;` -> Mapping of each virtual machine to its respective zone.
   - `array[1..NoZones, 1..NoZones] of int: ZoneLatency;` -> Latency matrix between zones (in ms).
   - `array[1..NoZones, 1..NoZones] of int: EgressCostPerGB;` -> Data transfer cost between zones.
   - `array[1..NoComponents, 1..NoComponents] of int: TrafficVolume;` -> Estimated data exchange between components.
   - `int: MaxAllowedLatency;` -> SLA threshold for WordPress <-> MySQL communication.

B. New / Modified Constraints:
   - Zone Anti-Affinity / Dispersion:
     For any component set requiring high availability (e.g., MySQL, Varnish):
     `forall(z in 1..NoZones) ( sum(k in 1..VM where VMZone[k] == z)(AssignmentMatrix[MySQL, k]) <= 1 );`
     (Ensures no two MySQL replicas share the same AZ).
   - Latency SLA Constraint:
     `forall(k1, k2 in 1..VM where AssignmentMatrix[Wordpress, k1] == 1 /\ AssignmentMatrix[MySQL, k2] == 1)`
     `( ZoneLatency[VMZone[k1], VMZone[k2]] <= MaxAllowedLatency );`

C. Objective Function Update:
   - Minimize total cost = (Sum of VM leasing prices) + (Sum of inter-zone egress traffic costs).
   - `solve minimize sum(k in 1..VM)(Price[k]) + sum(z1, z2 in 1..NoZones)(InterZoneTraffic[z1, z2] * EgressCostPerGB[z1, z2]);`


5. POSSIBLE IMPLEMENTATION ROADMAP FOR THE IDE LLM
--------------------------------------------------------------------------------
1. Extend `GeneralVariables.mzn` and input data parsers in `proj.py` to ingest zone maps and traffic matrices.
2. Implement AZ-assignment and dispersion predicates in a new or updated `.mzn` module.
3. Integrate latency SLA checks and network cost calculations into the objective function.
4. Validate model correctness with small instances before scaling up solver timeouts.

PS: Developing all of these extensions might be more complex than initially expected. Bearing this in mind, the user will ask the LLM
to start by specific parts of the extension. The LLM MUST NOT try to solve everything at once.
